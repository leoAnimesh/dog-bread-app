# Performance

Measured on 18 Sep 2026: Expo SDK 57, React Native 0.86.3, Hermes, iPhone 17 simulator
(iOS 27), macOS host.

## Bundle analysis

Reproduce with `npm run bundle:analyze`. It runs `expo export --source-maps`, then
`scripts/bundle-report.mjs`, a dependency-free source-map decoder that attributes every
generated byte to the package it came from.

### Optimisation applied

The first export weighed **2,995 KB / 1,838 modules** (4.0 MB of Hermes bytecode).
`react-native-reanimated` (737 KB), `react-native-worklets` (90 KB) and
`react-native-gesture-handler` (103 KB) made up 31 % of the bundle, yet the app used none of
them. A `GestureHandlerRootView` in the root layout pulled them in. Removing that import cut the
bundle to **2,004 KB / 1,391 modules (−33 %)** and 3.1 MB of bytecode. The packages stay
installed because expo-router lists them as peers, but nothing imports them.

What remains is standard for an Expo Router app: `react-native` core (561 KB) and
`expo-router`, which includes React Navigation (451 KB).

## Cold start to interactive

The start-up path (`useAppBootstrap`):

1. Open SQLite.
2. Run one `SELECT payload FROM breeds` for all 283 rows, plus reads for groups and sync metadata.
3. Load the results into the store.
4. Hide the splash screen.

Network work starts only after the list is on screen. The entire dataset is about 1.5 MB of JSON
text, so reading it is fast. Fonts load in parallel and are ready before the first paint, so text
never swaps fonts on screen.

## List rendering

Why each of the 283 rows is heavy, and what the app does about it, is covered in DECISIONS.md
under *List performance*: fields computed once at mapping time, memoised fixed-height rows, group
headers as a separate FlashList item type, and only thumbnails in the list.

## Image cache footprint

On the simulator, after a full sync, scrolling the list and opening several detail screens and
galleries, the cache directory held **159 files, 4.5 MB**. Rough sizes per image: a thumb is
about 4–15 KB, a medium 40–80 KB, a large 150–400 KB. The 60 MB LRU budget therefore holds every
thumb plus more than 100 large images before it starts deleting files.

## Memory

Measured on a **Release build** (`npx expo run:ios --configuration Release`), iPhone 17 simulator,
using `footprint -p <pid>`. This reports `phys_footprint`, the same figure as Xcode's memory gauge.

| Scenario | Footprint |
| --- | ---: |
| Cold start on a fresh install, full 6-page sync, list idle with thumbnails loaded | 100–108 MB |
| Peak during that session (`phys_footprint_peak`) | **108 MB** |

That is under the 150 MB target. For comparison, the same session in Expo Go measured ~800 MB
RSS, because it includes the Expo Go shell, the dev-mode runtime and the debugger. Don't use
Expo Go numbers for this.

Not covered by this measurement: scrolling the full list and opening detail screens. From here
the simulator can't be driven by touch, and iOS blocks deep links behind an "Open in…?" prompt.
The Xcode memory-gauge recording below covers those interactions.
